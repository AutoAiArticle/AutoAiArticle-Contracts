## 第一部分：背景与目标

### 1.1 系统全景

AutoAiArticle 正在从 Python 单体拆分为 8 个独立部署的 Cloudflare 子工程：

```
Scanner(热点采集,已完成) → Materials(资料检索) → Writer(写作) → QualityGate(质量评分)
                                                    ├→ ImageGen(生图)
                                                    └→ Publisher(导出)
Console(管理后台，聚合各服务)
```

服务之间只通过 HTTPS + HMAC 签名通信。**契约包 @autoai/contracts 是所有服务共享的唯一"语言定义"**：每个服务通过 npm 依赖它，发送方用它构造/序列化事件，接收方用它解析/校验事件。

### 1.2 本工程要交付什么

一个独立 git 仓库（建议名 `AutoAiArticle-Contracts`），内容为：

1. npm 包 `@autoai/contracts`：全部跨服务事件的 zod schema、HMAC 签名/验签纯函数、错误码分类、幂等键规则
2. golden fixtures：每个事件至少 1 个合法 + 1 个非法样本
3. 双向校验测试：合法样本必须解析通过，非法样本必须按预期错误码拒绝
4. CI：lint + typecheck + test 全绿才允许打 tag 发版

**本工程不部署任何 Worker、没有任何数据库、不含任何业务逻辑（评分、准入、决策）。** 它只被"安装"，不被"运行"。

### 1.3 成功标准

- Scanner 仓库的投递 payload 能被 `hotspotCandidateSchema` 解析通过（用真实样本回填 fixture）
- 主工程的 HMAC 待签串规则与包内 `hmac.ts` 逐字节一致（交叉验证测试）
- 任何一个服务安装本包后，能在自己的 CI 里跑通 fixtures 双向校验
- 发版流程：改 schema → 测试 → git tag → 消费方升级，全程不超过 10 分钟人工操作

## 第二部分：需求规格

### 2.1 功能需求

#### FR-1 事件 Schema（zod v3）

以下 **7 个事件**为 v1.0 必须交付的契约（hotspot-candidate、qualified-event、writing-request、quality-verdict、image-request、publish-request、candidate-feedback）。字段定义**逐字段取自现有两工程的真实代码**（来源已标注），不得凭空发明字段。

**schema_version 类型按事件独立**：hotspot-candidate 等新契约用 number literal `1`（沿用 Scanner 队列消息的 schema_version 语义），qualified-event 用 string `"1.0"`（沿用主工程 pydantic 契约语义）。这是有意的沿用而非疏漏——各事件迁移时保持与各自来源系统一致，消费方按 SUPPORTED_SCHEMA_VERSIONS 声明的类型校验。

**FR-1.1 hotspot-candidate（Scanner → Materials）**

来源：Scanner `src/domain/delivery.ts` 的 `buildCandidateDeliveryPayload` 实际产物 + `src/domain/contracts.ts`。以下为真实字段：

```ts
{
  schema_version: 1,                          // number literal 1
  event_type: 'hotspot_candidate',            // string literal
  event_id: string,                           // `toutiao:{sourceTopicId}`
  candidate_version: number(int, ≥1),
  notification_type: 'initial' | 'update' | 'degraded',
  source: { platform: 'toutiao', board: 'hotboard', url: string | null },
  topic: { title: string(1..200), source_tags: unknown /* Scanner 侧自由透传字段（delivery.ts L60 直接透传 input.sourceTags），
              契约层不承诺结构——注意 Scanner contracts.ts 的 normalizedTopicSchema 里它是 string[]，
              但投递 payload 未经该 schema 约束，接收方不得假设它是数组 */, ai_category: string | null },
  observed: { at: string(ISO), rank: number(int ≥1), first_seen_at: string(ISO),
              hot_value?: number | null },   // 三态（取自真实序列化路径，见下方说明）
  trend: { score: number(0..100), reasons: string[] },
  requirements: { needs_source_verification: boolean, do_not_treat_as_verified_fact: true },
  idempotency_key: string,                    // `toutiao:{sourceTopicId}:{candidateVersion}:{notificationType}`
  ai_review:                                  // 两态判别联合，来源 delivery.ts L73-84（真实代码只有以下两种，无 failed 分支）
    | { status: 'unavailable' }
    | { status: 'succeeded', writing_score: int(0..100),
        score_breakdown: { timeliness: 0..20, information_gain: 0..20, audience_fit: 0..15,
                           verifiability: 0..15, expandability: 0..15, competition: 0..5,
                           risk: 0..10 },
        summary: string(≤120), entities: {name, type}[](≤20),
        risk_level: 'allowed' | 'requires_authoritative_source' | 'requires_manual_review' | 'blocking',
        risk_flags: string[](≤20), search_queries: string[](≤10) },
  evidence?: { verified: false, note: string,
               items: { source: 'internal_recent' | 'internal_history' | 'web_search',
                        title: string, snippet: string | null, url: string | null,
                        similarity: number | null, meta?: Record<string, unknown> }[](≤6) }
}
```

约束（区分两类来源）：
- **schema 约束**（Scanner `contracts.ts` 已有，zod superRefine 实现）：
  - `score_breakdown` 七项之和必须等于 `writing_score`（contracts.ts L46-54）

**`observed.hot_value` 三态语义**（实施与 fixture 回填必读，源自真实序列化路径逐环核实）：
- Scanner 侧链路：`hot_value_num`(bigint) → `?.toString() ?? null` 存入 ai_jobs.payload_json（feature-service.ts）→ `typeof x === 'string' ? x : null` 取出（ai-service.ts）→ `if (x !== null) observed.hot_value = Number(x)`（delivery.ts L41-42）
- 由此产生三种真实形态：**① 键缺失**（hotValue 为 null 时不设键）；**② number**（正常解析）；**③ 值为 null**（上游存了非数字字符串时 `Number()` 得 NaN，`JSON.stringify(NaN)` 序列化为 null 且**键保留**）
- zod 定义必须写成 `z.number().nullable().optional()`——只写 optional 会拒绝形态③，导致真实 payload 解析失败（恰好卡住验收标准"真实样本回填 fixture"）
- **`trend.reasons` 注入语义**：hotValue 为 null 时 Scanner 自动追加 `'hot_value_unparseable'`（delivery.ts L48-49），接收方不得假设 reasons 只含 trend 语义标记，也不应将其视为错误
- **构造逻辑约束**（Scanner `delivery.ts` L66-68 的发送方行为，**不是接收方 schema 校验**）：
  - `needs_source_verification = (notification_type === 'degraded') || (ai_review.risk_level === 'requires_authoritative_source')`
  - 接收方 schema **不得**将其实现为 superRefine——否则"degraded 且 risk_level 恰为 requires_authoritative_source"等合法 payload 会被误拒。需要时只作日志观测，不作校验

```ts

                keywords: string[](≤30), time_expressions: string[](≤30) }  // 各项 ≤100 字符
  },
  trend: { first_seen_at, last_seen_at, score: 0..100, trend_score: 0..100,
           source_count: int≥1, source_codes: string[](≤20), best_rank: int≥1 | null },

              reason_codes: string[](1..20), reason_summary: string(≤1000) },

                对齐主工程 field_validator), title≤300, source_name≤200,
                published_at?, observed_at?, is_authoritative: boolean }[](1..20)

```

`url` 校验细节（对齐主工程 `inbound_event.py` L77-87 的 `_validate_url`）：
- scheme 必须是 `http`/`https`，且解析后 `netloc` 非空；长度 1..2000
- **语法级安全红线**（zod refine 可完成的全部）：拒绝 `file:`/`data:` 等非白名单 scheme（已被上一条覆盖）、带凭证（userinfo）的 URL、字面量内网主机名（`localhost`、`127.0.0.1`、`169.254.` 前缀、RFC1918 字面 IP）
- **⚠️ 语义边界（执行者必读）**：以上只是语法级拒绝。真正的 SSRF 防护——DNS 解析后命中私网 IP 段、重定向到内网、云元数据 IP 等——**需要网络操作，契约包 NFR-1 禁止副作用，做不了也不该做**。运行时 SSRF 防护是接收方（Materials 抓取层）的职责，契约包不越界。不要试图在 zod 里"挡住 SSRF"

`occurred_at` 及所有 datetime 字段：**必须带时区偏移**（`z.string().datetime({ offset: true })`）。

**这是一项有意收紧的语义决策**（不是对 pydantic 的忠实翻译），决策依据：主工程 pydantic 层实际接受 naive datetime（已实测验证），但数据库全列为 TIMESTAMPTZ（已核实 `timezone=True`）——naive 值写入时由驱动按会话时区解释，语义随环境漂移，在分布式系统里是隐患。因此：
- 新契约（writing-request、quality-verdict 等）：从第一天强制 `offset: true`
- 旧链路兼容（Scanner→主工程的 qualified-event）：**若** Materials 适配层需接收主工程可能产生的 naive 值，由适配层在解析前补时区（默认 UTC 或 Asia/Shanghai，按业务约定），不要为此放宽契约 schema 本身
- fixtures 必须各含一个带 `+08:00` 与带 `Z` 的样本，证明两种偏移写法均可接受

`delivery_id` 幂等语义：Materials 收到相同 delivery_id 的重复请求必须返回首次结果（见 FR-4）。

**FR-1.4 quality-verdict（QualityGate → Writer）**

新契约，判定规则**以主工程代码实测为准**（`app/core/config.py` L65-69 唯一权威阈值 + `pipeline.py` L448-493 实际判定逻辑）：

阈值（config.py）：
```text
ai_risk_pass_score = 40        # AI 痕迹通过线
ai_risk_rewrite_score = 65     # AI 痕迹改写线（不含，见下）
originality_pass_score = 80    # 原创度通过线
fact_risk_pass_score = 35      # 事实风险通过线
value_pass_score = 85          # 价值观通过线
```

AI 痕迹分组合（pipeline.py L457-466，**实测存在 0.70/0.30 权重**）：
```text
ai_risk = int(rule_score * 0.7 + model_trace_score * 0.3)
# model_trace_score 来自 AI 审稿（ai_client 为 None 或调用失败时为 0）
```

判定为**二段式，无 ">80 拒绝" 独立档**（pipeline.py L487-493）：
```text
overall_passed = ai_risk ≤ 40 AND originality ≥ 80 AND fact_risk ≤ 35 AND value ≥ 85
rewrite_required = ai_risk > 40 AND ai_risk ≤ 65
# ai_risk > 65 时：rewrite_required=false 且 overall_passed=false → 文章状态直接 REJECTED
```

注意：改写循环的次数上限（MAX_DE_AI_REWRITES=2，pipeline.py L60/L428）是 **Writer 侧流程控制**，不是 quality-verdict 的字段——verdict 只报告分数与判定，不含重试次数语义。

```ts
{
  schema_version: 1,
  evaluation_id: string(uuid),
  article_draft_id: string,
```

来源：Scanner `src/domain/contracts.ts` 的 `feedbackSchema`（**逐字段照搬，Scanner 已在用**）：

```ts
{
  schema_version: 1,
```

四个 ID 字段的语义区分（接收方容易用错，必须区分）：
- `callback_id`：**本次回调请求自身的标识**（每次 HTTP 调用一个新 uuid，用于请求级追踪/重放审计）
- `receipt_id`：**被回调的那次投递在 Scanner 侧的回执 ID**（原投递响应返回的 receipt_id，用于定位是哪次投递的反馈）
- `event_id`：**事件本体标识**（与投递 payload 的 event_id 同值，一个事件可有多版本投递）
- `idempotency_key`：**原投递的幂等键**（与投递 payload 的 idempotency_key 同值，用于反馈去重）

约束（superRefine，照搬 Scanner contracts.ts L86-92）：
- `lifecycle_status='rejected'` 时 `rejected_reason` 必填
- `lifecycle_status ∈ {article_created, published}` 时 `article_id` 必填

#### FR-2 HMAC 签名模块

来源：主工程 `app/core/security.py` + docs《热点采集平台与主工程通信接口设计.md》第三节。**必须逐字节对齐，因为主工程验签代码已存在，包内实现若不一致则验签必败**。

六行待签串（`\n` 连接）：
```
{METHOD 大写}
{请求 path（含 /api/v1 前缀，不含 query）}
{X-AA-Timestamp，RFC 3339 UTC}
{X-AA-Nonce，UUID}
{X-AA-Content-SHA256，64 位小写 hex}
{原始请求体字节长度，十进制字符串}
```

API（全部纯函数，不依赖 Workers runtime 特有 API，node 与 workers 环境均可运行）：

```ts
export function buildCanonicalString(method: string, path: string, timestamp: string,
  nonce: string, bodySha256Hex: string, bodyLength: number): string;
export function computeSignature(secret: string, canonicalString: string): string;  // 'v1=' + hex
export function sha256Hex(body: Uint8Array | string): Promise<string>;              // Web Crypto
export async function signRequest(secret, method, path, body: Uint8Array): Promise<SignHeaders>;
  // 返回 { 'X-AA-Key-Id': keyId, 'X-AA-Timestamp', 'X-AA-Nonce', 'X-AA-Content-SHA256', 'X-AA-Signature' }
export async function verifyRequest(args: { keys: Record<string, string>, method, path,
  body: Uint8Array, headers: Record<string,string>, toleranceSeconds: number,
  maxBodyBytes: number }): Promise<VerifyResult>;
  // keys: keyId -> secret 映射（对应主工程 settings.inbound_event_hmac_keys 字典）。
  // 验签时从请求头 X-AA-Key-Id 取 key_id，不在 keys 映射中即返回 unknown_key_id；
  // 命中则用对应 secret 完成后续校验。这样保持纯函数可测（传入固定映射即可覆盖
  // "未知 key"、"key 轮换期间新旧并存"两类场景），接收方从自己的配置/Secret 读取映射。
  // VerifyResult = { ok: true, keyId } | { ok: false, code: SignatureErrorCode }
```

**`computeSignature` 返回值格式（明确，避免交叉验证对不上）**：返回 `'v1=' + 64 位十六进制小写`，与 Python `f"v1={digest}"`（security.py L67）完全一致。交叉验证向量比较的即此完整串。

验签顺序（与主工程 `inbound_auth.py` L20-60 **逐步对齐**，顺序不可调换）：
1. **method/path 校验**（inbound_auth.py L27-28）：`method === 'POST'` 且 `path` 为调用方声明的接收端点（如 `/api/v1/hotspot-candidates`）——注意主工程硬编码了 qualified-events 路径，契约包改为**参数化**（各服务端点不同），但校验必须在函数内第一步执行，返回 `invalid_request`
2. Content-Type 含 application/json
3. body 大小限制（`maxBodyBytes` 参数传入）
4. key_id **存在且已配置**：请求头 `X-AA-Key-Id` 的值不在 `keys` 映射中 → `unknown_key_id`（对齐 inbound_auth.py L38-40 的 `key_id not in settings.inbound_event_hmac_keys` 判定）
5. timestamp 窗口（`|now-ts| ≤ tolerance`）
6. nonce 为 UUID 格式
7. body 摘要比对（SHA-256 hex，小写）
8. HMAC 常量时间比较

常量时间比较实现（替代此前"双 SHA-256"方案的更优解）：对 Python 侧 `hmac.compare_digest(expected, provided)`（security.py L89）的等价实现——先将两串各自 UTF-8 编码，若长度不等**仍走完比较循环**（用长度差异结果与逐字节异或累积，最后统一返回），确保任何分支都不提前泄漏长度信息。禁止字符串 `===` 直接比较。错误码与 HTTP 状态映射：

| code | HTTP |
|---|---|
| unknown_key_id / invalid_signature / timestamp_expired | 401 |
| payload_too_large | 413 |
| unsupported_media_type | 415 |
| invalid_request | 400 |

#### FR-3 错误码与重试分类

来源：Scanner `src/domain/state-machine.ts` 的 `classifyRetry` + 主工程错误响应结构 `InboundErrorBody`。

```ts
export const ERROR_CODES = { ... } as const;
export function isRetryableCode(code: string): boolean;
// HTTP 状态分类（照搬 Scanner state-machine.ts classifyRetry L31-40）：
// 5xx/网络错误/超时 → 'network_or_5xx'
// 429 → 'rate_limited'
// 400/401/403/404 → 'auth_or_config'
// 其余 → 'final'（不重试）
export function classifyHttpStatus(status: number | null): RetryClass;

// 退避表（state-machine.ts BACKOFF_SECONDS L42-45，逐值照搬）：
//   rate_limited:    [60, 120, 300, 600, 1200, 1800]
//   network_or_5xx:  [30, 90, 180, 480, 900]
//   auth_or_config:  [120, 300, 600, 1200, 1800]
// 抖动公式（state-machine.ts L46-58，必须逐字节对齐否则两边重试节奏漂移）：
//   rate_limited 且有 Retry-After ≥0 时：Math.ceil(retryAfter * (1 + random() * 0.1))
//   其余：base = 表[min(attempt, 表长-1)]，返回 Math.max(1, Math.round(base * (0.8 + random() * 0.4)))
//   第 4 参 random 默认 Math.random，测试注入固定随机源
export function retryDelaySeconds(
  retryClass: Exclude<RetryClass, 'final'>,
  retryableFailureCount: number,
  retryAfterSeconds: number | null,
  random: () => number = Math.random
): number;
```

### 3.3 关键实现要点

**hmac.ts 与主工程逐字节对齐（最高优先级正确性要求）**

主工程 Python 参考（翻译时逐行对照）：

```python
# app/core/security.py（已存在，验收基准）
def build_inbound_canonical_string(method, path, timestamp, nonce, body_sha256_hex, body_length):
    return "\n".join([method.upper(), path, timestamp, nonce, body_sha256_hex, str(body_length)])

def compute_signature(secret, canonical_string):
    digest = hmac.new(secret.encode(), canonical_string.encode(), hashlib.sha256).hexdigest()
    return f"v1={digest}"
```

TS 实现（要点）：

```ts
// 六行待签串：注意 Python str(body_length) 是十进制字符串，TS 里 String(body.byteLength)
export function buildCanonicalString(method, path, timestamp, nonce, bodySha256Hex, bodyLength) {
  return [method.toUpperCase(), path, timestamp, nonce, bodySha256Hex, String(bodyLength)].join('\n');
}

export async function sha256Hex(body: Uint8Array): Promise<string> {
  // ⚠️ Uint8Array 可能是视图（有 byteOffset / 长度 != buffer 长度），
  // 直接把 .buffer 传给 subtle.digest 会算错。必须先拷贝出精确切片：
  const copy = body.byteOffset === 0 && body.byteLength === body.buffer.byteLength
    ? body.buffer
    : body.buffer.slice(body.byteOffset, body.byteOffset + body.byteLength);
  const digest = await crypto.subtle.digest('SHA-256', copy);
  return [...new Uint8Array(digest)].map(b => b.toString(16).padStart(2, '0')).join('');
}
```

**交叉验证的字节陷阱**：Python 侧 `b'{"a":1}'` 是 7 个字节（无空格无换行）；TS 侧必须对**完全相同的字节序列**算摘要。测试向量 JSON 里同时存放 `body` 字符串与 `body_length`，TS 断言 `new TextEncoder().encode(body).byteLength === body_length` 后再进签名流程。

**交叉验证向量（tests/hmac.spec.ts 的核心）**：固定 secret/timestamp/nonce/body，用 Python 生成期望签名写进测试文件，TS 实现必须产出相同结果。生成方式：

```bash
# 在主工程根目录运行，产出测试向量 JSON
python -c "
import hashlib, hmac, json
secret='test-secret'; body=b'{"a":1}'
body_sha=hashlib.sha256(body).hexdigest()
canonical='\n'.join(['POST','/api/v1/inbound/qualified-events','2026-08-30T10:00:00Z','92dc1749-4d96-4f32-b76b-7cbcd730ac07',body_sha,str(len(body))])
sig=compute_signature(secret, canonical)  # from app.core.security
print(json.dumps({'secret':secret,'body':'{"a":1}','expected_signature':sig,'canonical':canonical}))
"
```
